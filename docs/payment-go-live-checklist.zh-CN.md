# new-api 支付联调与上线前检查清单

更新时间：2026-04-15

## 1. 适用范围

本清单适用于当前这套第一版官方扫码支付实现：

- 支付宝官方二维码支付
- 微信支付官方 Native 支付
- PC 端展示二维码
- 用户手机扫码完成充值
- 仅用于普通充值
- 不包含订阅、退款、代扣、分账等能力

## 2. 当前代码前提

当前代码基础已经具备：

- 后端支付接口已实现
- 前端二维码弹窗已实现
- 订单状态轮询已实现
- 本地后端可通过 `go build ./...`
- 前端可通过 `bun run build`

上线前不要再假设“代码应该没问题”，而是要逐项验证：

- 商户参数是否真实可用
- 回调地址是否公网可达
- 支付成功后订单状态是否正确更新
- 前端是否能在支付成功后正确刷新额度

## 3. 商户与资质准备清单

### 3.1 支付宝

你需要确认以下事项已经完成：

- 已有可正常使用的支付宝商户主体
- 已开通适用于扫码支付的官方产品
- 已拿到 `AppId`
- 已生成应用私钥
- 已拿到支付宝公钥
- 已确认网关地址
- 已在支付宝后台配置异步通知地址
- 已确认签名方式与当前实现一致

### 3.2 微信支付

你需要确认以下事项已经完成：

- 已有可正常使用的微信支付商户号
- 已开通 Native 支付
- 已确认商户号 `MchId`
- 已确认应用标识 `AppId`
- 已拿到 API 证书序列号
- 已准备商户私钥
- 已配置 APIv3 Key
- 已下载并确认平台证书
- 已确认支付回调地址可配置

### 3.3 业务侧

你还需要确认：

- 充值业务主体合法合规
- 充值金额档位已经确定
- 充值说明文案已经确认
- 用户协议、隐私说明、退款口径已经准备

## 4. 服务器与网络准备清单

### 4.1 域名与 HTTPS

必须确认：

- 已有公网可访问域名
- 已配置 HTTPS
- 证书有效且未过期
- 支付回调地址为正式公网地址

示例：

```text
https://your-domain.com/api/alipay/notify
https://your-domain.com/api/wechatpay/notify
```

### 4.2 防火墙与代理

必须确认：

- 服务器出网正常
- 支付平台回调可以访问你的服务
- 反向代理不会拦截回调请求
- 反向代理不会错误改写回调路径
- 请求体不会被代理层截断

### 4.3 时间与日志

必须确认：

- 服务器系统时间准确
- 时区配置明确
- 应用日志可落盘或可检索
- 回调日志、下单日志、签名异常日志可定位

## 5. 后台配置项检查清单

### 5.1 支付宝官方配置

后台应检查并填写：

- `AlipayOfficialEnabled`
- `AlipayOfficialAppId`
- `AlipayOfficialPrivateKey`
- `AlipayOfficialPublicKey`
- `AlipayOfficialGateway`

确认标准：

- 开关已启用
- 密钥内容完整无截断
- 没有把测试环境参数填到正式环境
- 公钥私钥没有填反

### 5.2 微信支付官方配置

后台应检查并填写：

- `WeChatPayOfficialEnabled`
- `WeChatPayOfficialAppId`
- `WeChatPayOfficialMchId`
- `WeChatPayOfficialSerialNo`
- `WeChatPayOfficialPrivateKey`
- `WeChatPayOfficialAPIv3Key`
- `WeChatPayOfficialPlatformCert`

确认标准：

- 开关已启用
- 证书和私钥内容完整
- 序列号与证书匹配
- APIv3 Key 长度和内容正确
- 没有混用测试商户与正式商户参数

## 6. 接口与路由检查清单

需要确认以下接口在正式环境中可用：

- `POST /api/user/alipay/pay`
- `POST /api/user/wechat/pay`
- `POST /api/alipay/notify`
- `POST /api/wechatpay/notify`
- `GET /api/user/topup/status/:tradeNo`

检查要点：

- 路由已注册
- 网关与反向代理未拦截
- 回调接口不被登录鉴权误挡
- 响应状态码符合支付平台要求

## 7. 支付宝联调检查清单

至少完成以下验证：

- 可以正常发起下单
- 可以正常拿到二维码内容
- 手机扫码后能跳转支付宝支付页
- 支付成功后回调能到达服务端
- 服务端验签通过
- 对应充值订单状态更新成功
- 用户额度或余额正确增加
- 前端轮询能识别支付成功
- 重复回调不会重复加额
- 超时未支付订单不会误判成功

建议额外验证：

- 金额为最小充值档位时是否正常
- 金额为较大充值档位时是否正常
- 用户关闭二维码弹窗后再次查询是否正常

## 8. 微信支付联调检查清单

至少完成以下验证：

- 可以正常创建 Native 订单
- 可以正常拿到二维码链接
- 微信扫码后可正常拉起支付
- 支付成功后微信回调可到达服务端
- 回调验签成功
- 订单状态更新成功
- 用户额度或余额正确增加
- 前端轮询能识别支付成功
- 重复通知不会重复加额
- 用户未支付超时后状态保持正确

建议额外验证：

- 微信支付失败或取消时前端提示是否合理
- 平台证书更换后验签逻辑是否还能处理

## 9. 异常场景检查清单

上线前至少要人工验证以下情况：

- 回调地址错误
- 支付平台回调超时
- 商户私钥错误
- 支付宝公钥错误
- 微信平台证书错误
- APIv3 Key 错误
- 金额不合法
- 订单已支付后重复回调
- 用户刷新页面后重新打开充值页
- 用户扫码成功但前端弹窗提前关闭

验证目标：

- 服务端不崩溃
- 日志可定位
- 订单状态不会乱
- 不会重复加额

## 10. 前端体验检查清单

你当前只做 PC 端二维码，所以重点应放在以下体验项：

- 二维码弹窗打开正常
- 支付方式切换清晰
- 支付中提示明确
- 轮询频率合理
- 支付成功后提示清晰
- 支付失败或超时后提示清晰
- 弹窗关闭后不会出现脏状态
- 刷新页面后充值记录可追踪

建议重点检查：

- Chrome
- Edge
- 常见国内 Windows 桌面环境

## 11. 数据与订单一致性检查清单

必须确认：

- 每个支付单号全局唯一
- 支付成功只加一次额度
- 支付状态变更有明确日志
- 订单金额与充值金额一致
- 订单未支付时不会提前入账
- 轮询查询和回调处理结果一致

如果数据库中已有历史充值逻辑，还要确认：

- 新支付方式不会破坏旧充值记录查询
- 充值历史页面可以兼容新订单状态

## 12. 运维上线检查清单

上线前建议完成：

- 备份当前配置
- 备份数据库
- 记录当前部署版本
- 记录当前提交号
- 记录支付配置修改人和修改时间
- 为关键日志设置检索关键词

## 13. 正式上线步骤建议

建议按下面顺序执行：

1. 在测试环境填入真实或沙箱参数
2. 完成支付宝全链路联调
3. 完成微信支付全链路联调
4. 验证重复回调与异常场景
5. 合并功能分支到 `stable/v0.12.9`
6. 从稳定分支部署到正式环境
7. 先用小金额做一次真实支付验证
8. 确认到账、记录、前端展示全部正常
9. 再开放给正式用户使用

## 14. 上线后首日观察项

上线后的第一天，不要只看“能不能支付”，还要看：

- 下单成功率
- 支付成功率
- 回调成功率
- 重复通知情况
- 用户投诉与工单情况
- 金额入账是否准确
- 是否存在卡单、漏单、重复加额

建议至少保留这些观察入口：

- 应用日志
- 反向代理日志
- 数据库订单记录
- 支付平台后台交易记录

## 15. 回滚预案

上线前必须明确：

- 如果官方支付配置异常，是否可以快速关闭开关
- 如果支付回调异常，是否可以立即暂停新支付入口
- 如果前端二维码流程有问题，是否可以回退到上一个稳定版本
- 如果只关闭官方支付，原有其他支付方式是否仍可保留

理想状态是：

- 支付方式可单独开关
- 发布包可快速回滚
- 数据库无破坏性结构风险

## 16. 一句话结论

对你当前这套第一版实现来说，上线前最关键的不是继续改代码，而是把以下三件事逐项做实：

- 商户参数真实可用
- 回调公网链路稳定
- 支付成功后的订单与额度更新绝不重复、不丢失
