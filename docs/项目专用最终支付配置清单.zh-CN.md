# `new-api` 项目专用最终支付配置清单

更新时间：2026-04-20

## 1. 这份清单是按什么前提写的

这份文档不是泛泛而谈，而是基于你这轮对话里最现实、最稳妥的目标方案来写的。

我这里采用的默认前提是：

- 你当前已经研究过 `ikuncode` 的 `ZPAY` 链路
- 你希望长期目标切到支付宝官方直连 + 微信官方直连
- 但你不想一刀切，所以迁移期保留 `ZPAY` 当备用通道
- 如确有需要，人工充值只作为兜底，不作为主链路

也就是说，这份“最终配置清单”针对的是下面这套推荐方案：

> 正式目标：支付宝官方直连 + 微信官方直连为主，`ZPAY` 在迁移期作为备用，人工充值可选开启但不做主入口。

如果你后面明确决定：

- 完全不用 `ZPAY`
- 或完全不用官方直连
- 或只做人工充值

那你再回头对照：

- `docs/支付配置示例大全.zh-CN.md`

做删减即可。

---

## 2. 先说最终建议，不绕弯

对你这个项目，我最推荐的最终落地顺序不是“先删旧再上新”，而是：

### 第一阶段：并行稳定

- 支付宝官方直连上线
- 微信官方直连上线
- `ZPAY` 保留为备用
- 人工充值可不开，或只给客服兜底

### 第二阶段：官方主用

- 钱包页优先展示官方支付
- `ZPAY` 只保留备用意义
- 观察一段时间成功率与到账率

### 第三阶段：再决定是否下线 `ZPAY`

- 只有在官方回调、查单、到账都稳定后
- 才考虑清理旧 `epay` 配置

所以这份文档会分成两部分：

1. 迁移期最终配置
2. 稳定后精简配置

---

## 3. 迁移期最终配置清单：我最推荐你先用这套

这套适合现在立刻落地。

## 3.1 通用设置

### 必填字段

```text
ServerAddress = 你的正式 HTTPS 业务域名
CustomCallbackAddress = 可选；若有单独 API 域名则填，没有可留空
Price = 你的实际充值换算单价
MinTopUp = 你的最小充值金额
```

### 推荐示例

```text
ServerAddress = https://pay.example.com
CustomCallbackAddress = https://api.example.com
Price = 7.3
MinTopUp = 1
```

### 这部分的结论

- `ServerAddress` 必须先正确
- 如果没有明确需要，不必强行填 `CustomCallbackAddress`

---

## 3.2 官方支付配置

这是未来的主链路。

### 支付宝必须具备

```text
AlipayOfficialEnabled = true
AlipayOfficialAppId = 你的支付宝开放平台 AppId
AlipayOfficialGateway = https://openapi.alipay.com/gateway.do
AlipayOfficialPrivateKey = 你的支付宝应用私钥 PEM
AlipayOfficialPublicKey = 你的支付宝公钥 PEM
```

### 微信必须具备

```text
WeChatPayOfficialEnabled = true
WeChatPayOfficialAppId = 已和当前商户号绑定的 AppID
WeChatPayOfficialMchId = 正式微信支付商户号
WeChatPayOfficialSerialNo = 商户 API 证书序列号
WeChatPayOfficialPrivateKey = 商户私钥 PEM
WeChatPayOfficialAPIv3Key = 32 位 APIv3 Key
WeChatPayOfficialPlatformCert = 微信支付平台证书 PEM
```

### 这部分的结论

- 支付宝官方和微信官方都应作为主链路打开
- 当前项目已经支持这两条链路，不需要你再自己造一套前端支付流程

---

## 3.3 `ZPAY` 备用配置

这部分只在迁移期保留。

### 保留这些字段

```text
PayAddress = 你的 ZPAY 网关地址
EpayId = 你的 ZPAY 商户 ID
EpayKey = 你的 ZPAY 商户密钥
```

### 推荐写法

```text
PayAddress = https://zpayz.cn
EpayId = 你的实际商户ID
EpayKey = 你的实际商户密钥
```

### 为什么现在不要删

因为迁移期最怕的是：

- 官方链路某天回调异常
- 微信参数有一项填错
- 线上一时半会儿修不完

这时候你还可以临时让用户走旧备用通道。

---

## 3.4 `PayMethods` 最终建议

迁移期我建议你不要清空，而是改成“备用命名”，避免自己和用户搞混。

### 推荐配置

```json
[
  {
    "name": "支付宝（备用）",
    "type": "alipay",
    "color": "rgba(var(--semi-blue-5), 1)"
  },
  {
    "name": "微信（备用）",
    "type": "wxpay",
    "color": "rgba(var(--semi-green-5), 1)"
  }
]
```

### 为什么这样配

- 当前项目会自动追加官方支付方式
- 你不用自己往 `PayMethods` 里手动写 `alipay_official` / `wxpay_native`
- 旧支付入口保留，但名称一眼就知道它只是备用

---

## 3.5 人工充值的最终建议

### 我的建议

默认可以不开。

只有在下面情况之一成立时，才建议开启：

- 你需要客服兜底
- 你担心官方与 `ZPAY` 同时异常时完全没备用
- 你确实能接受人工审核成本

### 如果开启，建议这样配

```text
ManualTopUpEnabled = true
ManualTopUpAlipayQRCode = 可公网访问的支付宝收款码图片 URL
ManualTopUpWeChatQRCode = 可公网访问的微信收款码图片 URL
ManualTopUpInstructions = 付款后等待人工审核到账
```

### 如果不开

建议：

```text
ManualTopUpEnabled = false
ManualTopUpAlipayQRCode = 留空
ManualTopUpWeChatQRCode = 留空
ManualTopUpInstructions = 留空
```

---

## 3.6 充值档位最终建议

如果你现在没有特别复杂的运营策略，建议用稳妥版。

### 推荐 `AmountOptions`

```json
[10, 20, 50, 100, 200, 500]
```

### 推荐 `AmountDiscount`

```json
{
  "100": 0.98,
  "200": 0.95,
  "500": 0.9
}
```

### 推荐 `TopupGroupRatio`

如果你暂时不做复杂分组，最简单是：

```json
{
  "default": 1
}
```

如果你已经有 VIP 组：

```json
{
  "default": 1,
  "vip": 1.05,
  "svip": 1.1
}
```

## 4. 迁移期的“最终状态”长什么样

如果一切按推荐方案落地，那么你的项目在迁移期应该表现成这样：

### 用户看到的效果

- 钱包页能看到支付宝官方入口
- 钱包页能看到微信官方入口
- 钱包页如果还看到旧入口，名字上会明确标“备用”
- 人工充值如果开启，也只是辅助入口

### 后端应该具备的能力

- 官方支付宝下单正常
- 官方微信下单正常
- 官方回调正常
- 官方订单状态轮询正常
- `ZPAY` 备用通道仍可跑通

### 运营应该知道的事

- 主入口是官方支付
- 备用入口是旧 `epay/ZPAY`
- 人工充值不是主通道

## 5. 稳定后精简配置：等官方稳定再切成这套

只有当官方链路已经稳定运行一段时间后，才建议切到真正的“最终精简版”。

## 5.1 可以保留的字段

### 通用

```text
ServerAddress
CustomCallbackAddress（若确有需要）
Price
MinTopUp
AmountOptions
AmountDiscount
TopupGroupRatio
```

### 官方支付

```text
AlipayOfficialEnabled = true
AlipayOfficialAppId
AlipayOfficialGateway
AlipayOfficialPrivateKey
AlipayOfficialPublicKey

WeChatPayOfficialEnabled = true
WeChatPayOfficialAppId
WeChatPayOfficialMchId
WeChatPayOfficialSerialNo
WeChatPayOfficialPrivateKey
WeChatPayOfficialAPIv3Key
WeChatPayOfficialPlatformCert
```

## 5.2 可以逐步清理的字段

如果你确定不再需要旧 `ZPAY`：

```text
PayAddress
EpayId
EpayKey
```

如果你确定不再需要旧入口：

```json
[]
```

也就是把 `PayMethods` 清空。

如果你确定不再需要人工充值：

```text
ManualTopUpEnabled = false
ManualTopUpAlipayQRCode = 留空
ManualTopUpWeChatQRCode = 留空
ManualTopUpAlipayAmountQRCodes = 留空
ManualTopUpWeChatAmountQRCodes = 留空
ManualTopUpInstructions = 留空
```

## 6. 我最推荐你最终保留的两套实际方案

为了方便你执行，我把最终建议压缩成两个真实可选版本。

## 6.1 版本 A：最稳妥版

适合现在立刻执行。

### 保留

- 官方支付宝
- 官方微信
- `ZPAY` 备用

### 可选

- 人工充值兜底

### 适合原因

- 风险最低
- 出问题能回退
- 最符合你当前过渡期状态

## 6.2 版本 B：精简生产版

适合官方稳定之后。

### 保留

- 官方支付宝
- 官方微信

### 清理

- `ZPAY`
- 旧 `PayMethods`
- 人工充值（如果不再需要）

### 适合原因

- 结构更干净
- 对账更清晰
- 用户更不容易走错入口

---

## 7. 这份“项目专用最终清单”对应的实际落地动作

如果你问我“现在下一步就干什么”，我建议按下面这 6 步做：

1. 先把 `ServerAddress` 和官方参数全部填好
2. 打开 `AlipayOfficialEnabled` 和 `WeChatPayOfficialEnabled`
3. 暂时保留 `PayAddress`、`EpayId`、`EpayKey`
4. 把 `PayMethods` 改成“备用命名版”
5. 做支付宝 / 微信 / `ZPAY` 各 1 笔真实小额联调
6. 稳定一段时间后，再决定是否清掉旧 `epay`

---

## 8. 一句话结论

如果只给你一句最适合你当前项目的最终建议，那就是：

> 现在先把官方直连做成主链路，把 `ZPAY` 留作迁移期备用，不要急着删旧配置；等真实支付、真实回调、真实到账稳定后，再把项目精简成纯官方支付。
