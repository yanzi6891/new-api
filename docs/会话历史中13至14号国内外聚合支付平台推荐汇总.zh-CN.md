# 会话历史中 13 至 14 号国内外聚合支付平台推荐汇总

更新时间：2026-04-20

> 说明：这份文档整理的是当前可见会话上下文里，围绕 4 月 13 至 14 号那轮“聚合支付平台 / 国际支付平台 / 官方直连路线”讨论所形成的推荐结论。  
> 它不是逐字逐句的原始聊天记录转录，而是把当时提到的平台、推荐语境、适用场景和推荐强度重新系统归纳。

## 1. 先说结论

当时那轮讨论，其实不是简单地“推荐某一家平台”，而是按场景分了两大方向：

- **国内充值 / 网站扫码 / 旧 `new-api` 兼容优先**
  - 更偏向：
    - 兼容 `epay / 易支付` 协议的聚合支付平台
    - 或者直接做支付宝 / 微信官方直连
- **出海 / 国际支付 / 海外开发者收款 / 订阅**
  - 更偏向：
    - `Stripe`
    - `Adyen`
    - `Checkout.com`
    - `Airwallex`
    - `dLocal`
    - `Paddle`
    - `PayPal / Braintree`
    - `Worldpay`

如果把当时的推荐压缩成一句话，就是：

> 国内场景，短期更推荐“旧 `epay` 聚合平台或官方扫码直连”这两条路线；国际场景，更推荐按业务类型在 `Stripe`、`Adyen`、`Checkout.com`、`Airwallex`、`dLocal`、`Paddle`、`PayPal/Braintree` 等平台里选主链路与补充链路。

---

## 2. 当时的推荐逻辑，不是“一份名单通吃所有场景”

前面那轮推荐之所以会同时出现国内外很多平台，是因为当时讨论的是：

- 你的项目可能既有国内充值需求
- 又有可能延伸到国际支付 / 出海 / 海外订阅

所以当时推荐时，实际上是按下面这些维度分流的：

- 你主要做国内还是海外
- 你是充值型业务还是订阅型业务
- 你更看重快上线，还是更看重长期可控
- 你需要的是网站扫码，还是国际卡支付，还是平台分账，还是税务合规托管

也正因为如此，当时提到的平台可以分成几层：

### 2.1 核心主推荐

是指在某个场景下，当时最值得优先考虑的平台。

### 2.2 强备选

是指在特定场景下非常值得一起对比的平台。

### 2.3 类别示例

是为了帮你理解“市面上还有哪些类型的平台”而举到的名字，不代表当时已经做了逐家深度推荐。

## 3. 当时推荐过的国外平台：重新系统整理

下面这部分，主要还原你记得的“国外聚合/国际支付平台推荐”。

## 3.1 `Stripe`

### 当时的推荐级别

- **核心主推荐**

### 当时为什么推荐它

在当时的讨论里，`Stripe` 基本属于国际支付方向的默认首选之一，原因主要是：

- 文档和 API 体验强
- 开发者友好
- 适合 SaaS、API 平台、数字产品、出海独立站
- 支持：
  - 卡支付
  - 订阅
  - Checkout
  - Webhooks
  - Connect 平台分账

### 当时适合的场景

- 海外开发者收款
- 出海 SaaS
- 数字产品
- API 平台
- 订阅收费

### 当时的定位

如果你的场景偏：

- 出海
- 开发者产品
- API / SaaS

那 `Stripe` 基本属于当时最优先建议保留和优先评估的平台。

---

## 3.2 `Adyen`

### 当时的推荐级别

- **强备选 / 企业级主选**

### 当时为什么推荐它

`Adyen` 当时被放在更偏企业级和全渠道场景里，原因主要是：

- 全球收单能力强
- 统一线上线下能力强
- 企业级稳定性强
- 平台型、品牌型、零售型企业很常拿来对标

### 当时适合的场景

- 中大型跨国企业
- 全球品牌
- 全渠道零售
- 对统一线上线下收单要求高的业务

### 当时的定位

如果不是典型创业团队，而是更偏：

- 企业级
- 多国家
- 多渠道
- 复杂支付架构

那 `Adyen` 会比 `Stripe` 更值得一起认真比。

---

## 3.3 `Checkout.com`

### 当时的推荐级别

- **强备选**

### 当时为什么推荐它

当时推荐它的原因主要是：

- 全球线上支付能力比较均衡
- API 化程度高
- 在跨境电商和中大型线上业务里很常作为 `Stripe` / `Adyen` 的对比项

### 当时适合的场景

- 跨境电商
- 中大型线上支付业务
- 希望比较多个国际 PSP 的团队

### 当时的定位

它不是所有团队的第一默认选择，但在国际支付选型里，属于一个非常合理的强备选。

---

## 3.4 `Airwallex`

### 当时的推荐级别

- **强备选**

### 当时为什么推荐它

因为它不只是支付，还更强调：

- 多币种账户
- 跨境资金管理
- 换汇
- 全球资金流协同

### 当时适合的场景

- 跨境卖家
- 出海品牌
- 需要强资金管理能力的团队
- 不只是收款，还很在意多币种资金流和结算效率的团队

### 当时的定位

如果你的需求不仅仅是“收款”，还包括：

- 多币种结算
- 跨境资金管理
- 财务资金流优化

那它在当时的推荐里就比很多纯收款网关更值得看。

---

## 3.5 `dLocal`

### 当时的推荐级别

- **区域型强备选**

### 当时为什么推荐它

因为它在讨论里被定位为：

- 更适合新兴市场本地支付方式覆盖的平台

尤其是：

- 拉美
- 中东
- 非洲
- 某些亚洲新兴市场

### 当时适合的场景

- 重点扩张新兴市场
- 目标用户不集中在欧美成熟卡支付市场
- 需要覆盖本地支付方式

### 当时的定位

它通常不是“全球唯一主选”，而更像：

- 用来补足 `Stripe` / `Adyen` 在某些地区本地支付覆盖不足的问题

---

## 3.6 `Paddle`

### 当时的推荐级别

- **订阅 / SaaS / 数字产品方向核心推荐**

### 当时为什么推荐它

因为当时讨论里明确区分了：

- 纯 PSP
- `MoR`（Merchant of Record）

而 `Paddle` 被放在：

- 软件订阅
- 数字内容
- SaaS 出海
- 想减少税务与合规负担

这一类场景里重点推荐。

### 当时适合的场景

- 出海 SaaS
- 数字产品
- 软件订阅
- 不想自己处理过多全球税务与法定销售责任的团队

### 当时的定位

如果你最在意的是：

- 少折腾全球税务
- 少承担一部分法定销售主体责任

那么当时 `Paddle` 会被放得很靠前。

---

## 3.7 `PayPal / Braintree`

### 当时的推荐级别

- **补充型推荐**

### 当时为什么推荐它

因为在欧美消费市场里，`PayPal` 本身就是转化工具，不只是支付方式。

### 当时适合的场景

- 欧美 C 端用户较多
- 你希望提高钱包支付转化
- 你需要把 `PayPal` 作为辅助支付方式补上

### 当时的定位

通常不是建议它单独承担所有复杂支付能力，而是：

- 作为主 PSP 的补充
- 提升支付方式覆盖和转化率

---

## 3.8 `Worldpay`

### 当时的推荐级别

- **企业级强备选**

### 当时为什么推荐它

因为它属于比较典型的全球企业级收单 / PSP 选项，经常在大型商户的国际支付选型里出现。

### 当时适合的场景

- 超大商户
- 传统大型零售
- 全球线上线下并行业务

### 当时的定位

更偏企业项目型、全球化重型支付架构，而不是中小团队第一优先默认值。

---

## 3.9 其他作为国际扩展视野提到过的平台

当时或后续延伸讨论里，还出现过一些国际名字，用来补充国际平台视野，例如：

- `Nuvei`
- `Rapyd`
- `PPRO`
- `FastSpring`

这些名字更多属于：

- 国际支付选型扩展清单
- 补充型视野

不是当时对你项目最核心的第一优先推荐。

---

## 4. 当时推荐过的国内平台：重新系统整理

下面这部分是你这次额外要求补充的“包括国内平台”的总结。

## 4.1 兼容 `epay / 易支付` 协议的平台

### 当时的推荐级别

- **国内短期上线方向的核心推荐类别**

### 当时为什么推荐它

因为 `new-api` 旧支付链路原生就更适合这类平台：

- `/api/user/pay`
- `/api/user/epay/notify`
- `go-epay`

这些都说明当前项目接这类平台成本最低。

### 当时适合的场景

- 站内充值
- 网站扫码支付
- 先快速上线
- 先少改代码

### 当时的定位

这不是“某一家”，而是当时国内路线里最先推荐的**平台类别**。

后来在真实案例分析里，这个类别被具体落到了：

- `ZPAY`

---

## 4.2 `ZPAY`

### 当时的推荐级别

- **后续通过真实链路分析识别出的具体实例**

### 它在讨论中的位置

需要特别强调：

- 最开始推荐聚合支付平台时，不是先点名 `ZPAY`
- 后来在分析 `ikuncode` 真实支付链路时，才确认它实际用的是：

```text
zpayz.cn
```

也就是：

```text
ZPAY
```

### 它为什么重要

因为它后来成为了：

- “兼容 `epay` 协议聚合平台”这个大类的一个真实具体实例

---

## 4.3 `Ping++`

### 当时的推荐级别

- **国内开发者 / 平台型聚合服务商示例**

### 当时为什么提到它

因为它很适合作为：

- 统一 API
- 平台支付层
- 开发者型聚合支付

这一类服务商的代表示例。

### 当时适合的场景

- 平台型业务
- 多支付通道统一接入
- 开发团队想做统一支付层

### 当时的定位

更偏“开发者平台型聚合支付服务商”的代表，不是你当前 `new-api` 国内充值场景的第一默认选项，但绝对属于当时有价值的参考平台。

---

## 4.4 `PayJS`

### 当时的推荐级别

- **国内聚合收款示例平台**

### 当时为什么提到它

它被提到的主要语境是：

- 帮你建立“国内还有哪些常见线上聚合收款平台”的认知

### 当时的定位

更偏示例和扩展认知，而不是当时对你项目的主推平台。

---

## 4.5 `富友`

### 当时的推荐级别

- **国内收单 / 聚合支付市场玩家示例**

### 当时为什么提到它

因为在讲中国大陆常见支付服务商、收单服务商、聚合平台形态时，`富友` 是一个典型名字。

### 当时适合的场景

更偏：

- 支付服务商
- 收单服务
- 线下或平台型支付方案视角

### 当时的定位

更像：

- 行业玩家示例
- 选型视野补充

而不是：

- 你当时明确要求我专门做深度分析的平台

---

## 4.6 `拉卡拉`

### 当时的推荐级别

- **门店型聚合收单平台示例**

### 当时为什么提到它

因为它是中国大陆很典型的：

- 门店型
- 终端型
- 传统收单型

服务商代表。

### 当时适合的场景

- 线下门店
- 终端设备
- POS
- 到店零售

### 当时的定位

主要用于说明：

- 市场上的“聚合支付平台”不全是 API 型的
- 还有很多是偏线下经营与收单服务的平台

---

## 4.7 `汇付天下`

### 当时的推荐级别

- **平台型 / 清结算型强备选**

### 当时为什么提到它

因为在“平台业务、分账、清结算、行业解决方案”这一层面，`汇付天下` 是国内常见参考项。

### 当时适合的场景

- 平台化交易
- 分账
- 行业支付方案
- 清结算能力要求较强的业务

### 当时的定位

更偏“平台和结算能力型玩家”，不是你当前最轻量的第一起步路线，但在扩展方案里很重要。

## 5. 当时国内外平台推荐的核心差异

前面那轮讨论里，其实国内和国际平台推荐逻辑差异很大。

## 5.1 国内侧更看重什么

主要看：

- 你是不是做国内用户充值
- 你是不是要支付宝 / 微信扫码
- 你是不是想少改现有 `new-api` 代码
- 你是不是希望先用聚合平台过渡

所以国内推荐的核心逻辑是：

- `epay` 兼容平台优先看兼容性和上线速度
- 官方直连优先看长期可控性

## 5.2 国际侧更看重什么

主要看：

- 你是订阅、SaaS、数字产品还是跨境电商
- 你是要卡支付还是本地支付方式
- 你要不要税务和销售主体责任托管
- 你要不要平台分账或资金管理

所以国际推荐的核心逻辑是：

- `Stripe` 偏开发者主选
- `Adyen` / `Checkout.com` / `Worldpay` 偏企业级
- `Airwallex` 偏跨境资金流
- `dLocal` 偏新兴市场
- `Paddle` 偏 SaaS / 订阅 / 税务合规托管
- `PayPal/Braintree` 偏钱包支付补充

---

## 6. 如果把当时的推荐按场景重新压成清单

## 6.1 国内充值 / 网站扫码 / `new-api` 旧链路兼容

优先顺序更接近：

1. 兼容 `epay` 的聚合支付平台
2. 支付宝 / 微信官方直连
3. 其他更重型的平台型支付服务商

## 6.2 出海 SaaS / 开发者平台 / 国际卡支付

优先顺序更接近：

1. `Stripe`
2. `Adyen`
3. `Checkout.com`
4. `PayPal / Braintree` 作为补充

## 6.3 跨境品牌 / 多币种资金管理

优先顺序更接近：

1. `Airwallex`
2. `Stripe`
3. `Adyen`

## 6.4 新兴市场覆盖

优先顺序更接近：

1. `dLocal`
2. `Stripe`
3. `Adyen`
4. `Airwallex`

## 6.5 SaaS / 订阅 / 税务与销售主体责任压力大

优先顺序更接近：

1. `Paddle`
2. `Stripe Billing`
3. `Adyen`

## 6.6 线下门店 / 到店经营 / 终端设备

更偏向：

- `拉卡拉`
- `富友`
- 其他门店型 / 收单型平台

## 7. 当时真正的“主推荐”有哪些

如果把那轮讨论里真正最核心的推荐抽出来，大概可以压成下面这张表。

| 场景 | 当时的主推荐 | 说明 |
| --- | --- | --- |
| 国内、尽快上线、少改 `new-api` | `epay` 兼容聚合平台 | 最贴近旧链路 |
| 国内、长期稳定 | 支付宝 / 微信官方直连 | 长期主链路更优 |
| 国际、出海 SaaS / API 平台 | `Stripe` | 默认主推荐 |
| 国际、企业级 / 全渠道 | `Adyen` | 企业级强项明显 |
| 国际、中大型线上业务 | `Checkout.com` | 强备选 |
| 国际、跨境资金流 | `Airwallex` | 资金管理能力强 |
| 国际、新兴市场 | `dLocal` | 本地支付覆盖强 |
| 国际、订阅 / 数字产品 / 少管税务 | `Paddle` | MoR 价值突出 |
| 国际、欧美钱包转化 | `PayPal / Braintree` | 常作为补充支付方式 |

---

## 8. 一句话版最终总结

如果把“13 至 14 号那轮国内外平台推荐”重新压成一句话，就是：

> 国内路线，当时重点推荐的是“兼容 `epay` 的聚合平台”与“支付宝/微信官方直连”两条主线；国际路线，当时重点推荐的是 `Stripe`、`Adyen`、`Checkout.com`、`Airwallex`、`dLocal`、`Paddle`、`PayPal/Braintree` 等按场景分工使用的平台，其中 `Stripe` 更像出海开发者产品的默认主选，`Paddle` 更像订阅型数字产品的合规化主选，`Adyen` 与 `Checkout.com` 更偏企业级强备选。
