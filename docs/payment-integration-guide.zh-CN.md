# new-api 支付接入调研与实施总结

更新时间：2026-04-13

## 1. 结论摘要

- 你的场景是国内用户为主，主要支付方式是支付宝和微信。
- 如果目标是尽快上线、尽量少改 `new-api` 源码，最省事的是继续兼容 `epay` 协议的聚合支付平台。
- 如果目标是长期稳定、链路可控、PC 端扫码支付体验更直接，那么接官方直连更合适。
- 你当前明确的业务范围是：
  - 只做 PC 端
  - 只展示支付宝二维码和微信二维码
  - 用户手机扫码支付
  - 只做普通充值，不做订阅
- 这个范围下，官方直连的改动量属于中等，不需要重构整套支付系统。

## 2. 你之前问过的问题与答案

### 2.1 `new-api` 里的“易支付 / epay”是什么意思

`epay` 在这个项目里不是某一家固定公司，也不是统一品牌官网，而是一类“兼容某种聚合支付接口协议”的支付网关接入方式。

在 `new-api` 现有实现中，你需要配置的是：

- `PayAddress`
- `EpayId`
- `EpayKey`
- 支付方式编码，如 `alipay`、`wxpay`

也就是说，`new-api` 原生支持的是“兼容 epay 协议的第三方支付平台”，不是“支付宝官方直连”或“微信支付官方直连”。

### 2.2 易支付官网是多少

没有统一官网。

准确说法是：

- 不是去找一个叫“易支付官方总站”的网站
- 而是去找“支持 epay 协议”的第三方支付服务商

所以 `PayAddress` 应该填的是你实际签约那家服务商提供的接口地址。

### 2.3 你用什么第三方支付平台

当时给你的建议是分两类看：

- 如果要尽快上线、尽量不改代码：找兼容 `epay` 的聚合支付平台
- 如果主要是国内用户，且你已经确定只做支付宝/微信扫码：优先考虑支付宝官方直连 + 微信支付官方直连

结论不是“必须用某一家固定第三方”，而是按你的目标选：

- 快速上线：聚合平台
- 长期维护和稳定：官方直连

### 2.4 `Merchant of Record / global payments / compliance` 是什么意思

- `Merchant of Record`
  - 指“名义商户 / 交易责任主体”
  - 谁负责收款、开票、税务、退款、风控、争议处理，谁就是 MoR
- `global payments`
  - 指全球收款能力
  - 一般覆盖国际信用卡、多币种、本地化支付方式
- `compliance`
  - 指合规
  - 包括 KYC、AML、税务、隐私、支付监管等

如果你的用户主要在国内，只做支付宝和微信扫码，那这些概念知道即可，不是第一阶段的重点。

### 2.5 支持国内支付宝/微信的平台有哪些

分两类：

#### 官方直连

- 支付宝当面付 / 预下单二维码
- 微信支付 Native 支付

#### 聚合平台

- 兼容 `epay` 协议的平台
- 富友、拉卡拉、Ping++、PayJS、一些 SaaS 聚合收款平台

对你当前项目而言：

- 想少改代码：聚合平台
- 想长期稳定：官方直连

### 2.6 官方直连对 `new-api` 源码改动大吗

如果是“全场景支付”，改动会比较大。

但你已经把范围收得很窄：

- PC 端二维码
- 支付宝扫码
- 微信扫码
- 普通充值

在这个范围下，改动量属于中等，主要集中在：

- 新增支付配置项
- 新增支付宝官方支付服务
- 新增微信官方支付服务
- 新增回调和查单接口
- 前端新增二维码弹窗和轮询

不需要重做订单表，也不需要重构整套充值逻辑。

### 2.7 目前只要 PC 端展示微信和支付宝二维码，手机扫码支付即可，这种最适合哪种接法

最适合：

- 支付宝：官方预下单二维码
- 微信：官方 Native 支付

这是最贴近你需求的方案。

原因：

- 不需要 JSAPI
- 不需要移动端 H5 拉起
- 不需要 App SDK
- 流程简单，用户理解成本低

### 2.8 微信、支付宝手续费怎么收，和聚合平台相比哪个更便宜

结论不是绝对的。

通常是：

- 官方直连：
  - 费率更透明
  - 长期更可控
  - 大多数情况下不会比聚合平台贵很多
- 聚合平台：
  - 有时会在某些行业或渠道给出更低报价
  - 但也可能叠加服务费、提现费、通道费、结算限制

所以真实判断标准不是看宣传页，而是看你能拿到的实际商务报价。

建议你比较这几项：

- 支付宝扫码费率
- 微信 Native 费率
- 退款手续费
- 提现/结算手续费
- 最低结算金额
- T+0 / T+1 / T+N 结算周期
- 是否有年费、开户费、接口服务费

## 3. 第一版实施方案

### 3.1 目标范围

第一版只做：

- PC 端充值
- 支付宝官方二维码
- 微信官方二维码
- 扫码支付
- 普通充值

暂不做：

- 订阅支付
- 手机 H5
- 微信 JSAPI
- App 内支付
- 聚合平台替换

### 3.2 后端设计

第一版新增两种支付方式：

- `alipay_official`
- `wxpay_native`

复用现有 `TopUp` 订单表，不新增数据库结构。

核心流程：

1. 前端发起充值请求
2. 后端创建本地订单
3. 后端调用支付宝/微信官方接口创建二维码订单
4. 后端返回二维码链接
5. 前端展示二维码
6. 用户扫码支付
7. 支付平台异步回调
8. 后端验签、校验金额、完成入账
9. 前端轮询订单状态补充兜底

### 3.3 前端设计

前端第一版采用：

- 充值页新增官方支付按钮
- 点击后先弹充值确认框
- 确认后弹二维码框
- 二维码框内轮询订单状态
- 成功后自动关闭二维码并刷新余额

### 3.4 为什么保留现有 `epay`

这样做的好处是：

- 不影响现有使用者
- 兼容已有支付配置
- 官方二维码和聚合支付可以并存
- 后期可以逐步切量

## 4. 已落地的第一版实现

当前代码已经开始落地第一版，核心方向是：

- 后端新增支付宝官方支付和微信官方 Native 支付服务
- 后端新增官方支付回调接口
- 后端新增官方支付订单状态查询接口
- 后台新增官方支付配置项
- 前端新增官方二维码支付弹窗
- 前端新增官方支付轮询逻辑

这一版仍然是“可运行的第一版实现”，后续还需要你用真实商户参数联调。

## 5. 后续联调清单

你拿到正式商户资料后，需要重点核对：

### 支付宝

- `AppId`
- 应用私钥
- 支付宝公钥
- 网关地址
- 异步通知地址

推荐通知地址：

- `/api/alipay/notify`

### 微信支付

- `AppId`
- 商户号 `MchId`
- 商户证书序列号
- 商户私钥
- `APIv3 Key`
- 微信平台证书
- 异步通知地址

推荐通知地址：

- `/api/wechatpay/notify`

### 功能联调

- 创建二维码是否成功
- 用户扫码后是否触发回调
- 验签是否通过
- 支付金额是否一致
- 订单是否从 `pending` 变为 `success`
- 用户额度是否正确入账
- 二维码过期后是否能正确显示失败/过期状态

## 6. 你的项目选择建议

如果你现在问“最终应该怎么选”，我的建议仍然是：

- 你现在这个阶段：先做官方扫码第一版
- 如果要快速备份方案：保留 `epay`
- 真正上线前：拿官方费率和聚合平台报价做一次对比

也就是说：

- 技术上，官方扫码第一版已经是对你最匹配的路线
- 商务上，再比较一次费率和结算条件
