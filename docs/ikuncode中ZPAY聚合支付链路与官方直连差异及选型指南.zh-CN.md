# `ikuncode` / `new-api` 中 `ZPAY` 聚合支付链路、官方直连差异与选型指南

更新时间：2026-04-19

## 1. 先说结论

- 你当前看到的 `ikuncode` 在线充值链路，不是“支付宝官方直连”或“微信支付官方直连”，而是**`epay / 易支付协议兼容的聚合支付链路`**。
- 这条链路里已经能明确识别出的聚合平台是 **`ZPAY`（`zpayz.cn`）**。
- 我之前提到的“聚合支付平台”，说的是一个**平台类型**，不是某一家固定公司；`ZPAY` 正是这个类型里的一个具体服务商。
- `ZPAY` 之所以会出现在链路中间，本质上是因为它在帮业务系统做三件事：
  1. 统一支付宝 / 微信两套支付入口；
  2. 提供兼容 `epay` 的统一接口，减少代码改造；
  3. 把商户入驻、支付渠道、收银台展示、部分风控和结算流程包装成一层中间服务。
- 所以它不是“技术上必须存在”的一层，而是**为了更快上线、降低门槛、兼容旧系统而主动引入的一层**。

## 2. 为什么可以判断 `ikuncode` 用的是 `ZPAY`

这个判断不是猜测，而是基于你提供的真实请求数据和项目代码逻辑交叉验证出来的。

### 2.1 你抓到的真实接口返回已经直接指向 `ZPAY`

你提供的请求链路里，前端先请求：

```http
POST https://api.ikuncode.cc/api/user/pay
Content-Type: application/json

{
  "amount": 1,
  "payment_method": "alipay"
}
```

随后接口返回的核心信息是：

```json
{
  "message": "success",
  "url": "https://zpayz.cn/submit.php",
  "data": {
    "money": "1.00",
    "name": "TUC1",
    "notify_url": "https://api.ikuncode.cc/api/user/epay/notify",
    "out_trade_no": "USRxxxx",
    "pid": "2025xxxxxxxx",
    "return_url": "https://api.ikuncode.cc/console/log",
    "sign": "xxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxx",
    "sign_type": "MD5",
    "type": "alipay"
  }
}
```

只看这一段，其实就已经足够说明：

- 后端并没有直接给前端返回支付宝官方订单号或微信官方 `code_url`
- 后端返回的是一组典型的 `epay` 风格字段
- 前端下一步不是直接展示官方二维码，而是把表单提交到 `https://zpayz.cn/submit.php`

这已经是标准的“第三方聚合网关跳转收银台”特征。

### 2.2 项目源码也正好对应这套旧 `epay` 流程

从 `new-api` 当前代码可以直接对应到这条链路：

- `web/src/components/topup/index.jsx`
  - 前端在普通在线支付场景下调用 `/api/user/pay`
  - 拿到返回的 `url` 和 `data` 后，动态创建 HTML `form`
  - 然后把表单 `POST` 到第三方支付网关
- `controller/topup.go`
  - 后端 `RequestEpay` 使用 `go-epay` 客户端构造支付请求
  - 生成 `notify_url`、`return_url`、`out_trade_no`
  - 返回第三方网关地址和签名参数
- `service/epay.go`
  - 回调地址会根据站点配置进行拼接
- `/api/user/epay/notify`
  - 明确就是旧的 `epay` 异步通知入口

换句话说，`ikuncode` 用的不是“项目自己直连支付宝 / 微信”，而是“项目调用 `epay` 兼容接口，再把用户带到第三方收银台”。

### 2.3 实际还原请求后，确实会先到 `ZPAY`，再跳到它自己的收银页

对你抓到的参数做真实还原后，`POST https://zpayz.cn/submit.php` 会先返回 `302`，再跳到一个腾讯云托管的收银页面：

```text
https://shangqing-...tcloudbaseapp.com/submit.html?info=...
```

这个 `submit.html` 并不是你的业务站点页面，而是 `ZPAY` 的前台收银展示页。页面再去解析 `info` 参数，展示支付二维码。

所以这条链路可以概括成：

```text
ikuncode 前端
-> POST /api/user/pay
-> 后端返回 zpayz.cn/submit.php + epay参数
-> 浏览器 form POST 到 zpayz.cn/submit.php
-> ZPAY 302 跳到自己的收银台页面
-> 收银台展示二维码
-> ZPAY/对应渠道支付完成后回调 ikuncode 的 /api/user/epay/notify
```

## 3. `ZPAY` 到底属于什么类型的平台

按照 `ZPAY` 官网和开发文档当前页面的公开描述，它属于一种：

> **兼容 `epay / 易支付` 协议的聚合支付服务商**

`ZPAY` 官网和开发文档当前可看到的关键信息包括：

- 官网宣称支持个人、个体工商户、企业接入支付宝 / 微信接口
- 官网宣称“兼容易支付接口，支持市面上大部分系统，无需额外开发”
- 开发文档明确给出：
  - 页面跳转支付入口：`https://zpayz.cn/submit.php`
  - API 支付入口：`https://zpayz.cn/mapi.php`
  - 参数风格包括 `pid`、`notify_url`、`return_url`、`sign`、`sign_type=MD5`

这和你抓到的 `ikuncode` 请求返回结构完全吻合。

### 3.1 它和我之前说的“聚合支付平台”是什么关系

关系很简单：

- 我之前说的是**类别**
- `ZPAY` 是这个类别里的**一个具体实例**

也就是说，之前不是“漏掉了另一个完全不同的技术路线”，而是：

- 之前说的是“兼容 `epay` 协议的聚合平台”
- 现在我们确认 `ikuncode` 具体选用的是其中的 `ZPAY`

### 3.2 `ZPAY` 和“泛 `epay` 聚合平台”的区别，主要不在协议，而在运营细节

从架构上讲，`ZPAY` 和其他 `epay` 兼容平台的共同点非常多：

- 都是第三方中间层
- 都尽量屏蔽支付宝 / 微信原生接口差异
- 都给你一个统一的支付网关地址
- 都让业务系统只处理统一签名、统一回调、统一下单

真正会拉开差异的地方，通常是这些：

- 开户门槛
- 是否支持个人主体 / 小微主体 / 个体工商户
- 渠道稳定性
- 费率与开户费
- 提现 / 结算规则
- 风控强度
- 售后支持
- 文档质量
- 对旧系统的兼容程度

所以从“技术协议”看，`ZPAY` 并没有脱离我之前说的那类平台；但从“具体供应商选择”看，它当然是一个有自己费率、渠道、风控和运营规则的独立服务商。

## 4. `ZPAY` 相比“官方直连”有什么优点和缺点

下面这张表，适合你直接拿来判断为什么有人会选 `ZPAY`，以及它为什么不是最终最优解。

| 对比项 | `ZPAY` / `epay` 聚合中转 | 支付宝 / 微信官方直连 |
| --- | --- | --- |
| 接入速度 | 快，老系统常常只改配置即可 | 慢，要做商户、应用、证书、密钥、回调、联调 |
| 代码改动 | 小，当前 `new-api` 旧流程几乎原生兼容 | 中等，需要走官方接口分支 |
| 支付入口 | 统一一个网关 | 支付宝、微信分别接 |
| 主体门槛 | 通常更低，部分平台宣称支持个人 / 小微 | 更看重正式商户能力、应用能力、资料合规 |
| 前端表现 | 常见是跳第三方收银台 | 可直接展示你自己的官方二维码弹窗 |
| 成本结构 | 常见是官方费率外再叠平台费、开户费或通道费 | 费率更透明，但前期接入和运营成本更高 |
| 可控性 | 中，受第三方平台政策、路由、风控影响 | 高，订单、渠道、对账、退款都更可控 |
| 稳定性来源 | 依赖中间平台本身的稳定性与渠道质量 | 直接依赖官方接口与自己系统 |
| 故障排查 | 链路更长，问题可能出在你、平台、上游渠道任一处 | 链路更短，定位更直接 |
| 合规和品牌感知 | 用户可能看到第三方收银台域名 | 用户更容易感知是你的站点官方支付 |

### 4.1 `ZPAY` 的主要优点

#### 对当前 `new-api` 项目最现实的好处

- **几乎不用重写旧支付链路**
  - 当前 `/api/user/pay` 就是为 `epay` 类网关准备的
  - 前端已经内置“拿回 `url` + `data` 后，自动构造表单并跳第三方收银台”的逻辑
- **一个接口统一支付宝 / 微信**
  - 对业务系统来说，下单参数差异会被中间层隐藏掉
- **入驻和上线往往更快**
  - 尤其对个人开发者、小团队、验证期项目更友好
- **省掉一部分复杂支付工程工作**
  - 包括不同渠道产品能力差异、部分路由、部分收银台页面处理

#### 对运营侧的现实好处

- 可以先验证“用户愿不愿意充值”
- 可以先验证“站内充值逻辑是否跑通”
- 可以先让后台财务、补单、回调流程稳定下来
- 正式量起来以后，再考虑迁移到官方直连

### 4.2 `ZPAY` 的主要缺点

- **多了一层供应商依赖**
  - 你的业务不只是依赖支付宝 / 微信，还依赖 `ZPAY`
- **费用通常不会是最低**
  - 很多聚合平台会在官方费率上再加平台费、开户费或渠道费
- **链路更长**
  - 订单创建、收银台展示、支付回调都多了一层
- **品牌和体验不够“自有化”**
  - 用户会看到第三方域名或第三方收银台
- **长期可控性弱于官方直连**
  - 某些功能、结算、路由、退款、风控口径由平台掌握

## 5. 为什么不直接对接支付宝、微信官方支付

这个问题要分成“理论上能不能”和“对你当前项目/主体来说值不值得、好不好做”两层看。

### 5.1 理论上可以，但不是一句“个人也能申请”就等于能直接落地

很多人会把下面几件事混在一起：

- 我有个人支付宝 / 微信号
- 我可以申请某种商家身份
- 我就能直接接网站充值接口
- 我就能把 `new-api` 里的官方支付一次性跑通

这四件事并不是同一件事。

### 5.2 微信支付这边，当前官方网站接入文档依然以经营主体接入为主

微信支付当前 PC 网站接入页面写得很明确：

- 支持**完成域名ICP备案的网站**接入支付
- 如需自行开发完成收款，可通过 **Native 支付** 生成二维码
- 申请材料列出的主体主要是：
  - 个体工商户
  - 企业
  - 党政机关 / 事业单位 / 社会组织等
- 如果要自行开发收款，通常还要把商户号与 `AppID` 绑定

这说明什么？

- 这套“普通商户自助接入网站支付”的官方路线，本质上仍然是**经营主体能力接入**
- 它不是“普通消费者个人微信号，直接拿来给网站做充值接口”这么简单

另外，微信支付合作伙伴文档里确实存在**小微商户进件**路线，但那是典型的**服务商协助入驻**模式，仍然不是“你什么都不用准备，天然就有官方直连能力”。

### 5.3 支付宝这边，个人和小主体的空间通常比微信更灵活，但仍然不等于零成本直连

支付宝开放平台当前“网页/移动应用”入口写得也很清楚：

- 先创建应用
- 再完成密钥、网关等开发配置
- 然后提交审核和上线

这说明支付宝官方直连至少要求你具备：

- 应用创建能力
- 密钥 / 签名配置
- 回调联调能力
- 产品签约 / 审核 / 上线流程理解

所以即便某些支付宝产品对个人主体更友好，也不代表：

- 完全不需要应用
- 完全不需要签约
- 完全不需要审核
- 完全不需要处理异步回调和证书 / 密钥

### 5.4 回到 `new-api` 这个项目，官方直连为什么没有被很多人直接作为第一选择

因为对这个项目来说，官方直连需要同时满足两类条件。

#### 条件一：主体和支付产品条件

你得真正具备这些东西：

- 支付宝可用的官方支付产品能力
- 微信支付可用的商户能力
- 可用于网站 / PC 扫码的产品权限
- 微信 `AppID` 与商户号绑定关系
- 备案域名、回调地址、正式站点环境

#### 条件二：技术和运维条件

你还得自己扛这些事情：

- 商户私钥 / 证书管理
- 签名与验签
- 统一下单
- 异步通知
- 主动查单
- 退款
- 对账
- 异常单处理
- 风控与交易投诉配合

对于个人开发者或小团队来说，这并不是“不能做”，而是**初期性价比经常不高**。

## 6. 为什么需要用 `ZPAY` 做一次中转

答案其实很现实：**为了降低当前项目的接入成本和运营门槛。**

### 6.1 从技术上看，它解决的是“旧系统兼容”问题

当前 `new-api` 的老在线支付流程，本来就是按 `epay` 兼容网关写的：

- 后端走 `/api/user/pay`
- 后端返回 `url + data`
- 前端自动 `form POST`
- 回调走 `/api/user/epay/notify`

如果继续接 `ZPAY`：

- 这套路几乎原封不动就能用
- 不需要把老支付逻辑整套推翻
- 不需要一开始就全面切到官方 SDK / 证书体系

所以 `ZPAY` 在这里承担的是“**把业务系统和官方支付细节隔开**”的角色。

### 6.2 从业务上看，它解决的是“先跑起来”问题

对很多小项目来说，先做的是：

- 用户能不能顺利充值
- 回调能不能到账
- 订单能不能自动入账
- 财务能不能核对
- 站点能不能先上线

如果这些都还没验证，直接投入官方直连，前期准备工作会比较重。

### 6.3 从主体条件看，它解决的是“官方门槛未完全满足”问题

有些团队会遇到：

- 还没有完整企业主体
- 还没有准备好完整支付材料
- 还没把 `AppID`、证书、备案域名都理顺
- 想先做小规模试运行

这时候，聚合平台就相当于给你提供了一条“先接入、后升级”的过渡路线。

## 7. `ZPAY` 和官方直连，哪个更适合你

这里不讲空话，直接按场景选。

### 7.1 适合继续先用 `ZPAY` 的情况

如果你符合下面这些特征，继续用 `ZPAY` 往往更合理：

- 你现在最优先目标是**尽快上线**
- 你不想大改当前支付代码
- 你暂时没有完整的支付宝 / 微信官方商户参数
- 你现在是个人开发者、小团队、试运营阶段
- 你接受第三方中转、第三方收银台、第三方平台依赖

### 7.2 适合尽快切官方直连的情况

如果你符合下面这些特征，建议把 `ZPAY` 视作过渡方案：

- 充值已经是核心收入链路
- 订单量开始变大
- 你希望费率更透明
- 你希望支付品牌感更强
- 你希望自己掌握订单、回调、退款、对账与风控节奏
- 你已经具备或即将具备正式商户和应用能力

### 7.3 对这个项目更现实的落地建议

最稳妥的建议通常不是“二选一”，而是：

#### 第一阶段：保留 `ZPAY`，让业务先稳定

- 继续沿用旧的 `/api/user/pay` 流程
- 把充值、回调、补单、日志先跑顺
- 验证真实用户支付成功率

#### 第二阶段：并行上线官方直连

- 支付宝走 `alipay_official`
- 微信走 `wxpay_native`
- 新前端优先展示官方二维码支付
- 老 `epay` / `ZPAY` 保留为备用通道

#### 第三阶段：再决定是否下线 `ZPAY`

只有当下面都稳定后，再考虑完全切掉：

- 官方通道已稳定
- 回调已稳定
- 退款与对账已稳定
- 商户资料、证书、轮换流程都已规范化

## 8. 一句话回答你这三个核心问题

### 8.1 `ZPAY` 和之前说的聚合平台有什么区别

严格说，**没有路线级别的本质区别**。

之前说的是“兼容 `epay` 协议的聚合平台”这个大类，`ZPAY` 是其中一个具体供应商。

真正的差别主要在：

- 费率
- 开户门槛
- 主体支持范围
- 风控
- 稳定性
- 结算方式
- 售后支持

### 8.2 为什么不直接对接支付宝、微信官方渠道

不是不能，而是：

- 官方直连门槛更高
- 资料、应用、证书、回调、联调更复杂
- 微信对网站支付和商户能力要求更偏正式经营主体
- 对个人开发者和小项目来说，前期投入往往不划算

### 8.3 为什么需要 `ZPAY` 中转

因为它能：

- 兼容当前 `new-api` 的旧 `epay` 支付结构
- 降低主体和接入门槛
- 统一支付宝 / 微信两路支付
- 把一部分收银台和通道细节交给第三方处理

本质上，`ZPAY` 是一个**“更容易先跑起来”的折中方案**。

## 9. 如果你还想继续深挖，我下一步最建议查什么

如果你还想把这条链路继续查深，最值得继续确认的是：

### 9.1 `ZPAY` 最终落到的到底是哪种商户模型

比如：

- 官方普通商户
- 服务商模式下的小微 / 特约商户
- 某种平台内部分账 / 清算模式

这个单靠前端 `submit.php` 页面还无法完全确认。

### 9.2 想继续确认，需要哪些证据

最有效的是下面几类信息：

- 支付成功后的账单截图
- 支付页面显示的收款方名称
- 支付宝 / 微信账单里的商户名
- `ZPAY` 商户后台截图
- `ikuncode` 收到的异步回调原文

有了这些，才能进一步判断：

- 到底是不是独立商户
