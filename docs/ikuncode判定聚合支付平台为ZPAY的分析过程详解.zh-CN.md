## 4. 第一步：抓到真实下单请求，确认不是前端静态跳转

真正把分析从“猜测”推进到“证据判断”的，是你后面提供的真实请求数据。


请求体：

```json

  "amount": 1,
```

这个请求非常关键，因为它说明：

看到 `/api/user/pay` 这个接口时，可以先做出一个中间判断：

- `ikuncode` 的支付发起动作，是先由自己后端生成某种支付参数
- 然后再把这些参数返回给前端继续处理

这一步还不能说明是官方直连还是聚合支付，但它已经排除了“纯前端静态码跳转”。

## 6. 第三步：用项目源码交叉验证，请求结构与前端行为完全对上

为了避免只凭抓包“看起来像”，后面又对当前项目代码做了交叉验证。

这一步的目的不是重新猜，而是验证：

> 这条请求返回结构，是否真的符合 `new-api` 里旧 `epay` 支付链路的实现方式。

### 6.1 前端代码验证：`web/src/components/topup/index.jsx`

当前前端里，普通在线支付逻辑是：

1. 调用：

```text
/api/user/pay
```

2. 后端如果返回 `url + data`
3. 前端就动态创建 HTML `form`
4. 再把 `data` 作为隐藏字段提交到 `url`

也就是说，前端并不是自己构造支付二维码，而是：

- 把后端返回的网关地址和签名参数，直接提交给第三方支付页面

### 6.2 后端代码验证：`controller/topup.go`

后端里对应的是：

- `RequestEpay`
- `GetEpayClient`
- `EpayNotify`

核心逻辑是：

1. 接收前端的 `/api/user/pay`
2. 通过 `go-epay` 客户端生成下单参数
3. 拼出：
   - `notify_url`
   - `return_url`
   - `out_trade_no`
4. 返回：
   - 第三方支付 `url`
   - 对应签名参数 `data`

### 6.3 回调逻辑验证：`/api/user/epay/notify`

后端还明确存在：

- `/api/user/epay/notify`

这与抓到的真实返回值：

```text

```

是完全一致的。

### 6.4 这一步的意义

这一步非常重要，因为它说明：

- 你抓到的请求不是某个偶然页面行为
- 而是和当前项目旧 `epay` 支付实现完全对得上

换句话说，`ikuncode` 用的是：

- 当前项目原本就支持的那套旧 `epay` 聚合支付链路

而不是：

- 新加的官方支付宝二维码直连
- 新加的微信 Native 官方直连

虽然前面的证据已经足够确认“入口网关是 `zpayz.cn`”，但当时还继续往下查了一层，目的是确认：

### 7.2 这个现象说明什么

这说明：

- `submit.php` 不是一个可以直接访问的普通网页
- 它是一个**依赖 POST 参数的支付入口**

也就是说，它更像：

- 支付网关表单接收页

而不是：

- 最终用户看的收银页面

### 7.3 继续做的验证动作

后面根据你给的真实参数，把这些参数真正 POST 到：

### 7.5 这一步带来的新判断

这一步说明：

- `zpayz.cn/submit.php` 是真正的接单入口


这进一步加强了“它确实是第三方聚合支付平台”的判断。

## 10. 最终把整条链路串起来

把前面所有证据串起来后，整条链路可以还原为：

```text
1. 用户在 ikuncode 充值页选择支付宝
2. 前端 POST https://api.ikuncode.cc/api/user/pay
3. ikuncode 后端生成 epay 风格支付参数
4. 后端返回：
   - url = https://zpayz.cn/submit.php
   - data = pid/sign/notify_url/out_trade_no/type...
5. 前端创建 HTML form
6. 浏览器 form POST 到 https://zpayz.cn/submit.php
7. ZPAY 返回 302
8. 浏览器跳到腾讯云托管的 submit.html?info=...
9. submit.html 解码 info，展示支付宝二维码
10. 用户扫码支付
11. ZPAY/对应渠道完成后回调 https://api.ikuncode.cc/api/user/epay/notify
12. ikuncode 后端更新本地充值订单状态
```

当这 12 步都能对上时，“聚合支付平台是 `ZPAY`”这个结论就不是模糊判断，而是完整链路上的明确节点识别。

## 11. 为什么可以排除“这是支付宝/微信官方直连”

这个问题很关键，因为很多人会误以为：

- 最终页面展示的是支付宝码
- 那就等于它是支付宝官方直连

这个推理是不成立的。

### 11.1 与官方直连不符的地方

本次链路中，有几个地方和官方直连明显不一致：

#### 不一致 A：下单入口不是官方接口，而是 `ikuncode -> /api/user/pay`

官方直连通常会看到的是：

- 官方风格的后端接口命名
- 官方风格的请求和返回结构

而这里看到的是旧 `epay` 风格接口。

#### 不一致 B：返回值里直接给了 `zpayz.cn/submit.php`

如果是官方直连，通常不会返回一个第三方聚合平台域名作为支付入口。

#### 不一致 C：回调地址是 `/api/user/epay/notify`

如果是官方直连，通常会走：

- 支付宝官方回调逻辑
- 微信官方回调逻辑

而不是统一的 `epay` 回调入口。

#### 不一致 D：前端行为是“构造表单 POST 第三方网关”

这正是典型的旧 `epay` 网关行为。

### 11.2 所以正确结论是什么

正确结论不是：

- “它不是支付宝收款”

而是：

- “它不是业务系统自己直接对接支付宝官方接口”
- “它是先经过 `ZPAY` 这层聚合平台，再由聚合平台把支付展示给用户”

## 14. 这次分析方法本身可以怎么复用

这次其实也总结出了一套很好复用的支付链路分析方法。

以后再分析别的网站是不是用了某家聚合支付平台，可以按这个顺序来：

### 第一步：抓真实下单请求

看用户点支付后，请求的是哪个业务接口。

### 第二步：抓真实返回值

重点看：

- 返回的 `url`
- 参数名风格
- 回调地址

### 第三步：映射源码

把：

- 前端入口
- 后端下单
- 回调接口

三者对起来。

### 第四步：继续向下追跳转

把第三方支付入口真的请求一次，观察：

- 是 200 还是 302
- 是否还有下一级收银台

### 第五步：解码中间参数

如果有：

- `info`
- `token`
- `data`

这类编码字段，就继续解出来看实际订单对象。

### 第六步：区分“平台节点”和“最终支付展示”

不要因为最后展示支付宝二维码，就误判为“业务系统是官方直连”。
