# new-api 优化空间与风险报告

## 1. 总体判断

这个项目已经具备很强的平台能力，优点是功能完整、供应商适配丰富、业务场景覆盖广；缺点是代码规模和配置复杂度已经明显进入“平台级维护”阶段。

结论不是“它不能用”，而是：

- 它已经能用、而且功能很强
- 但后续要持续维护好，必须把测试、配置治理、前端性能和代码一致性补上

## 2. 本次观察到的高优先级优化点

| 优先级 | 问题 | 证据 | 影响 | 建议 |
| --- | --- | --- | --- | --- |
| P0 | 测试当前非全绿 | `go test ./...` 失败，问题集中在 `relay/channel/claude`、`relay/helper`、`service` | 说明核心中继链路已有回归风险 | 先修红测，再谈新增功能 |
| P0 | JSON 约定执行不一致 | 扫描到约 113 个 Go 文件直接引入 `encoding/json`，约 257 处直接调用 `json.Marshal/Unmarshal/NewDecoder` | 与项目“统一使用 `common/json.go`”约定不一致，后续替换 JSON 实现会非常困难 | 分阶段替换为 `common.Marshal` / `common.Unmarshal` / `common.DecodeJson` |
| P1 | 前端产物体积过大 | `bun run build` 生成的 chunk 中，`assets/index-BXLDB3bc.js` 约 7.3 MB，另有多个 1.8~1.9 MB chunk，Vite 明确给出 chunk warning | 首屏、缓存、弱网加载和浏览器性能都会受影响 | 增加更细粒度路由分包，拆分 Mermaid / 图表 / Markdown / Playground 重型依赖 |
| P1 | 安全默认值还可加强 | `main.go` 中 session cookie `Secure: false`；`controller/relay.go` 中 WebSocket `CheckOrigin` 直接返回 `true` | 生产环境下存在浏览器侧安全策略弱化风险 | 根据环境区分开发 / 生产默认值，并增加配置化控制 |
| P1 | 配置系统复杂且分散 | 启动期 env、全局变量、`OptionMap`、`setting/config` 同时存在 | 新人容易混淆，运行时配置一致性和可观测性较弱 | 明确“启动配置”和“运营配置”的边界，补一份统一配置矩阵文档 |

## 3. 中优先级优化点

## 3.1 Relay 适配器层需要更强的标准化

`relay/channel/` 下已有 37 个 provider / adaptor 目录，说明扩展能力很强，但也意味着：

- 新增供应商时重复劳动多
- 行为一致性容易漂移
- 错误处理和流式处理口径可能不统一

建议：

- 为 adaptor 抽出更统一的测试夹具
- 增加 golden tests
- 针对 OpenAI / Claude / Gemini / Task adaptor 建立基线行为测试

## 3.2 构建流程对 `web/dist` 有明显耦合

后端通过 `//go:embed web/dist` 内嵌前端产物，这样做部署简单，但也带来两个问题：

- 本地源码启动前必须确保 `web/dist` 存在
- 前后端构建顺序被强绑定

建议：

- 增加更明确的开发启动脚本
- 在 README 和本地开发文档中把这个约束写得更醒目
- 也可以考虑在开发模式下支持“无 dist 启动 + 外部前端代理”

## 3.3 测试覆盖与项目规模不匹配

本次看到的测试文件大约 23 个，而项目有：

- 528 个 Go 文件
- 大量中继适配器
- 多数据库兼容逻辑
- 大量运营与计费逻辑

这不是说“完全没测试”，而是测试密度相对平台复杂度偏低。

建议优先补：

- 渠道选择与重试
- 配额结算
- 协议转换
- 多数据库迁移
- 设置项导入导出

## 3.4 数据库兼容虽然有意识，但仍需持续审计

项目非常强调 SQLite / MySQL / PostgreSQL 三库兼容，这一点很好，但也意味着维护成本很高。

从代码看，已经存在一些数据库分支逻辑和原生 SQL 片段，主要集中在：

- 迁移
- 字段类型判断
- 时间函数
- SQLite 特殊处理

建议：

- 给关键迁移加三数据库 CI
- 把“必须兼容三库”的约束写入自动检查
- 对 raw SQL 做更集中审计

## 3.5 大文件和职责膨胀问题明显

例如：

- `router/api-router.go`
- `controller/channel.go`
- `controller/user.go`
- `controller/relay.go`
- `model/option.go`

这些文件职责都比较重。

建议：

- 按业务域继续拆分路由
- 按场景拆 controller
- 对设置项按模块拆更新逻辑
- 降低单文件认知负担

## 4. 低优先级但值得做的优化

## 4.1 清理历史遗留和潜在死代码

例如 `model/main.go` 中的 `createRootAccountIfNeed()` 当前没有实际调用，看起来像早期初始化路径残留。

这种逻辑不一定有 bug，但长期保留会增加阅读噪音。

## 4.2 文档与实现进一步对齐

当前文档、Docker、Go 版本、前端开发方式、支付配置说明都比较多，建议进一步统一：

- 哪些是快速体验路径
- 哪些是本地开发路径
- 哪些是生产部署路径

减少“能启动，但不知道该按哪种姿势启动”的情况。

## 4.3 前端开发插件按环境裁剪

`web/vite.config.js` 中的 `codeInspectorPlugin` 当前直接进入插件链。虽然这不一定造成严重问题，但可以考虑在开发模式启用、生产构建关闭，以缩小构建链复杂度。

## 4.4 更新前端基础数据

`bun run build` 给出 `Browserslist` 数据陈旧提示，这虽然不是功能性故障，但应当纳入常规维护。

## 5. 现阶段最值得优先落地的 6 件事

建议按这个顺序推进：

1. 修复当前红测，恢复 `go test ./...` 基线
2. 统一 JSON 包装层调用，清理直接 `encoding/json`
3. 压缩前端首屏体积，拆分大 chunk
4. 强化生产安全默认值：cookie secure、WS origin、密钥配置
5. 梳理配置治理：env / option / module config 的边界
6. 为 relay adaptor 建立更系统的回归测试框架

## 6. 哪些地方其实已经做得不错

虽然上面讲了很多优化点，但也要客观看到项目已经具备的成熟度：

- 分层结构基本成型
- 多数据库兼容不是口号，代码里有明确实现
- 多供应商适配深度很高
- 计费与运营功能已经形成闭环
- Web 控制台和 API 网关不是割裂的，而是同一套系统

这说明项目已经过了“从 0 到 1”阶段，接下来更像是在做“从 1 到 10”的工程治理。

## 7. 总结

如果从“功能完整度”来看，这个项目已经很强；如果从“长期可维护性”来看，最需要补的不是再接一个新供应商，而是：

- 测试稳定性
- 代码约定一致性
- 前端性能
- 配置治理
- 安全默认值

把这几件事做好，这个项目会从“功能很多的 AI 网关”进一步升级成“更稳的 AI 平台底座”。
