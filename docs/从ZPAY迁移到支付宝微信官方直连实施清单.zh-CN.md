# 从 `ZPAY` 迁移到支付宝/微信官方直连实施清单

更新时间：2026-04-19

## 1. 这份文档适合谁

这份文档适合下面这类场景：

- 你当前已经在 `new-api` 里接了 `ZPAY` 或其他兼容 `epay` 的聚合支付
- 现在想逐步切到支付宝官方直连 + 微信支付官方直连
- 你不想一次性硬切，担心用户支付中断
- 你希望按“先并行、再灰度、再切换”的方式稳妥上线

如果你还没有申请商户资料，先看：

- `docs/payment-static-qr-vs-merchant-account-guide.zh-CN.md`
- `docs/payment-merchant-application-materials-template.zh-CN.md`

如果你已经拿到商户参数，但不知道后台怎么填，配合看：

- `docs/payment-new-api-backend-fill-and-joint-debug-handbook.zh-CN.md`

---

## 2. 先看懂当前项目里的两条支付链路

### 2.1 你当前的旧链路：`ZPAY` / `epay` 聚合支付

当前旧链路是：

```text
前端
-> POST /api/user/pay
-> 后端按 epay 协议生成参数
-> 前端 form POST 到 ZPAY 的 submit.php
-> 用户进入第三方收银台
-> 第三方回调 /api/user/epay/notify
```

项目里对应的位置主要是：

- `controller/topup.go`
- `service/epay.go`
- `web/src/components/topup/index.jsx`

### 2.2 你准备切换的新链路：支付宝 / 微信官方扫码直连

当前项目里已经有第一版官方扫码支付实现：

```text
前端
-> POST /api/user/alipay/pay 或 /api/user/wechat/pay
-> 后端直接调用官方接口创建二维码订单
-> 前端显示二维码弹窗
-> 官方异步回调业务站点
-> 前端轮询订单状态
```

项目里对应的位置主要是：

- `controller/topup_official.go`
- `web/src/components/topup/index.jsx`
- `web/src/components/topup/modals/QRCodePaymentModal.jsx`
- `web/src/pages/Setting/Payment/SettingsPaymentGatewayOfficial.jsx`

这意味着：

- 你不是要“从零重做支付系统”
- 而是要把默认主链路从旧 `epay` 聚合支付，逐步迁移到官方扫码支付

---

## 3. 最重要的迁移原则

### 3.1 不要一刀切

最不建议的做法是：

- 上午申请好商户号
- 下午直接删掉 `ZPAY`
- 晚上让用户全部走新链路

这样最容易出问题：

- 回调还没打通
- 证书或密钥配置错误
- `AppID` 绑定关系不对
- 前端按钮显示了，但实际下单失败
- 支付成功了，但站内订单没入账

### 3.2 正确做法是“三阶段迁移”

#### 第一阶段：保留 `ZPAY`，把官方直连先并行接好

目标：

- 新旧链路同时存在
- 不影响当前充值能力
- 官方链路可以独立联调

#### 第二阶段：让真实用户逐步走官方直连

目标：

- 小流量验证
- 观察成功率、回调、投诉、补单、对账
- 保留 `ZPAY` 作为回退通道

#### 第三阶段：官方直连稳定后，再决定是否下线 `ZPAY`

目标：

- 确认官方链路已稳定承担主流量
- 再清理旧的 `epay` 配置和旧按钮

## 4. 小白可执行的迁移步骤

### 4.1 第一步：先把当前 `ZPAY` 旧链路状态记录下来

在改任何配置前，先把当前能跑通的旧支付配置备份一份。

至少记录这些内容：

- `PayAddress`
- `EpayId`
- `EpayKey`
- 当前 `PayMethods`
- 当前实际可用的回调地址
- `ZPAY` 商户后台的重要设置截图

为什么要先备份：

- 后面官方直连联调失败时，你可以快速切回
- 可以避免“改完之后连旧链路也回不去了”

建议同时确认一次旧链路确实还活着：

- 发起 1 笔小额支付
- 看能否跳到 `submit.php`
- 看订单是否能成功回调入账

### 4.2 第二步：准备官方直连所需主体与参数

#### 支付宝至少要准备

- 支付宝开放平台应用 `AppId`
- 应用私钥
- 支付宝公钥或证书能力
- 已签约可用的支付产品能力
- 可被公网访问的异步回调地址

#### 微信支付至少要准备

- 微信支付商户号 `MchId`
- 与商户号绑定的 `AppID`
- 商户 API 证书序列号
- 商户私钥
- `APIv3 Key`
- 可被公网访问的异步回调地址

如果这些材料你还没拿全，不建议开始切换。

### 4.3 第三步：先把站点基础地址配置正确

后台先检查这些基础项：

- `ServerAddress`
- `CustomCallbackAddress`（如有）

原因很简单：

- 官方支付和旧 `epay` 一样，都依赖正确的回调基础地址
- 地址错了，前端可能能出二维码，但支付成功后系统入不了账

你要重点确认：

- 是正式域名，不是内网地址
- 不是前端 Vite 地址
- HTTPS 证书正常
- 外网可访问

### 4.4 第四步：先填官方支付配置，但先不要立刻删除 `ZPAY`

当前项目里，官方支付建议先完整填好这两组：

#### 支付宝官方配置

重点通常包括：

- `AlipayOfficialAppId`
- `AlipayOfficialPrivateKey`
- `AlipayOfficialPublicKey`
- `AlipayOfficialNotifyURL`（若页面支持单独配置）
- 支付宝官方开关

#### 微信支付官方配置

重点通常包括：

- `WeChatPayOfficialAppID`
- `WeChatPayOfficialMchId`
- `WeChatPayOfficialSerialNo`
- `WeChatPayOfficialAPIv3Key`
- `WeChatPayOfficialPrivateKey`
- 微信支付官方开关

这里的详细填写说明，直接按这份文档逐项核对：

- `docs/payment-new-api-backend-fill-and-joint-debug-handbook.zh-CN.md`

注意：

- 这一步是“新增官方配置”
- 不是“删除旧 `ZPAY` 配置”

### 4.5 第五步：先确认前端已经能显示官方支付入口

当前前端已经区分了三类充值方式：

- 旧 `epay` 方式：如 `alipay`、`wxpay`
- 官方支付宝：`alipay_official`
- 官方微信：`wxpay_native`

你需要确认：

- 钱包页已经能显示“支付宝官方”“微信支付官方”入口
- 点击后弹出确认框
- 确认后能展示二维码弹窗

如果官方按钮一直不显示，优先检查：

- 后台官方支付开关是否打开
- 官方配置是否提交成功
- `ServerAddress` 是否已填写
- 前端是否已经部署到包含官方支付功能的版本

### 4.6 第六步：优先打通异步回调，不要只看二维码能否出来

很多人联调支付时，只看这一步：

- 点充值
- 出二维码
- 手机扫成功

但真正决定系统能否正式上线的，是下面这些：

- 支付成功后，订单状态是否从 `pending` 变成成功
- 用户余额或额度是否真的到账
- 重复回调是否安全
- 金额校验是否正确
- 失败单能否查出来

当前项目里，官方回调入口主要是：

- 支付宝：`/api/alipay/notify`
- 微信支付：`/api/wechatpay/notify`

旧 `ZPAY` / `epay` 回调入口是：

- `/api/user/epay/notify`

上线前一定要分别做 1 到 3 笔真实小额支付验证：

- 支付宝官方成功单
- 微信官方成功单
- 至少一笔旧 `ZPAY` 备份通道成功单

### 4.7 第七步：把官方直连先作为“优先展示”，但保留 `ZPAY` 备用

这是最稳妥的一步。

建议你这样做：

- 前端优先展示 `alipay_official` 和 `wxpay_native`
- 旧 `alipay`、`wxpay` 先不要马上彻底删掉
- 可以只让管理员、测试账号或少量用户先看到官方入口
- 保留一个可快速回退的旧通道

这样做的好处是：

- 一旦官方回调异常，可以马上切回旧链路
- 不会因为一处配置错误导致全站无法充值

### 4.8 第八步：观察 3 类核心数据，再决定是否切主链路

建议至少连续观察这些数据：

#### A. 下单成功率

看是否存在：

- 点支付后接口报错
- 二维码生成失败
- 某一个支付方式成功率明显偏低

#### B. 支付到账率

看是否存在：

- 用户说已支付，但系统没到账
- 回调偶发失败
- 金额校验失败

#### C. 运营处理成本

看是否存在：

- 补单增多
- 用户咨询明显变多
- 对账更难做
- 投诉变多

如果这三类数据都稳定，再考虑让官方直连承担主流量。

### 4.9 第九步：确认官方链路稳定后，再清理旧 `ZPAY` 配置

只有在下面条件都满足后，才建议清理旧配置：

- 支付宝官方直连稳定
- 微信支付官方直连稳定
- 回调已连续稳定运行
- 前端默认入口已经切到官方支付
- 已有明确回退方案

你可以逐步做这些清理：

1. 从 `PayMethods` 里移除旧的 `alipay`、`wxpay`
2. 保留一段时间配置备份
3. 确认没有订阅、旧页面、隐藏入口还依赖 `epay`
4. 再决定是否清空 `PayAddress`、`EpayId`、`EpayKey`

不建议一上来就删掉：

- `PayAddress`
- `EpayId`
- `EpayKey`

因为一旦官方链路有问题，你就失去最快的回退手段。

## 5. 你实际最该核对的配置清单

| 类别 | 必查项 | 通过标准 |
| --- | --- | --- |
| 域名 | `ServerAddress` | 正式 HTTPS 域名，可公网访问 |
| 回调 | `CustomCallbackAddress` | 若填写，必须真实可达 |
| 支付宝 | `AppId`、私钥、公钥/证书 | 可成功创建订单并收到回调 |
| 微信 | `AppID`、`MchId`、序列号、私钥、`APIv3 Key` | 可成功生成 Native 二维码并收到回调 |
| 前端 | 官方支付按钮 | 钱包页正常显示 |
| 订单 | 官方支付成功后入账 | 订单状态自动更新 |
| 兼容 | 旧 `ZPAY` 通道 | 在迁移期内仍可正常回退 |
| 日志 | 下单、回调、查单日志 | 可定位异常订单 |

## 6. 最常见的迁移翻车点

### 6.1 只配了支付参数，没检查回调地址

表现：

- 二维码能出来
- 用户也能扫
- 但系统不到账

根因通常是：

- 回调地址不可达
- 域名写错
- HTTPS 证书异常
- 反向代理没放通

### 6.2 微信 `AppID` 和商户号没绑定

表现：

- 微信配置看起来都填了
- 但 Native 支付创建失败或官方返回绑定关系异常

### 6.3 支付宝密钥或公钥配错

表现：

- 下单失败
- 回调验签失败

### 6.4 前端已经切了官方入口，但旧通道被你删太早

表现：

- 官方一出问题，线上无可用充值备份链路

### 6.5 忘了订阅或其他旧支付入口

当前项目里不只有普通充值，还可能有订阅侧 `epay` 逻辑。

所以清理旧配置前，还要确认这些入口是否仍在用：

- `controller/subscription_payment_epay.go`
- `web/src/components/topup/SubscriptionPlansCard.jsx`

如果订阅还在依赖 `epay`，就不能因为普通充值切官方了，就把整套旧配置直接清空。

## 7. 最稳的上线顺序

如果你想按最省心的顺序做，我建议按这个时间线：

### 第 1 天：只做配置和后台自查

- 补齐支付宝 / 微信商户资料
- 填完官方配置
- 不动旧 `ZPAY`

### 第 2 天：只做小额真实联调

- 支付宝 1 元测试
- 微信 1 元测试
- 分别验证下单、扫码、回调、入账
- 再测 1 笔旧 `ZPAY` 备用链路

### 第 3 天：小流量灰度

- 优先展示官方入口
- 少量用户试用
- 观察日志、到账、投诉

### 第 4 天到第 7 天：并行运行

- 官方做主入口
- `ZPAY` 做备用入口
- 每天核对成功率与异常单

### 稳定后：再考虑下线旧 `ZPAY`

- 删除旧支付方式显示
- 最后再清理 `epay` 配置

---

## 8. 对你这个项目最实用的一句话建议

如果你当前已经有 `ZPAY` 在稳定收款，最好的做法不是“立刻替换”，而是：

> 先把支付宝官方直连和微信官方直连并行接好，确认真实支付、真实回调、真实到账都稳定后，再逐步把默认流量从 `ZPAY` 切过去。

这样你既不会因为切换过猛影响收款，也能一步步把支付链路从“第三方中转”升级到“官方直连”。
