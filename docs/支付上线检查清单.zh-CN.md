# `new-api` 支付上线检查清单

更新时间：2026-04-19

## 1. 这份清单怎么用

这份清单不是原理说明，而是给你上线前逐条打勾用的。

建议你按 3 个阶段使用：

1. 上线前
2. 灰度中
3. 正式切换后

如果你当前正在从 `ZPAY` 迁移到官方直连，这份文档尤其适合直接照着过一遍。

建议配合这几份文档一起用：

- `docs/支付后台字段级填写对照表.zh-CN.md`
- `docs/支付配置示例大全.zh-CN.md`
- `docs/支付联调排错手册.zh-CN.md`
- `docs/从ZPAY迁移到支付宝微信官方直连实施清单.zh-CN.md`

## 2. 第一阶段：上线前检查清单

这一阶段的目标是：

- 配置完整
- 回调地址正确
- 小额真实支付能走通
- 有回退方案

### 2.1 域名与基础地址

- [ ] `ServerAddress` 已填写为正式 HTTPS 域名
- [ ] `ServerAddress` 不是 `localhost`、`127.0.0.1`、内网 IP、前端开发地址
- [ ] 如使用 `CustomCallbackAddress`，该地址也能公网访问
- [ ] 回调域名已通过实际浏览器或外部网络验证可达
- [ ] HTTPS 证书正常，没有过期或链不完整问题

### 2.2 支付模式选择

- [ ] 已明确当前上线模式是以下哪一种：
  - 只用 `ZPAY` / `epay`
  - 只用官方直连
  - 官方直连 + `ZPAY` 并行
  - 人工充值
- [ ] 团队内所有人都知道当前主链路是哪一条
- [ ] 不会把人工充值、旧 `epay`、官方直连三套模式混着对外宣导

### 2.3 旧 `epay` / `ZPAY` 配置

如果你还保留旧链路，检查这些：

- [ ] `PayAddress` 已填写真实第三方网关地址
- [ ] `EpayId` 已填写正确商户号
- [ ] `EpayKey` 已填写正确签名密钥
- [ ] `PayMethods` 中的旧支付入口和当前策略一致
- [ ] 已确认旧链路能成功完成一笔小额支付
- [ ] `/api/user/epay/notify` 回调地址在平台侧没有写错

### 2.4 支付宝官方配置

如果你启用了支付宝官方直连，检查这些：

- [ ] `AlipayOfficialAppId` 已填写正确
- [ ] `AlipayOfficialGateway` 仍为官方网关地址，未乱改
- [ ] `AlipayOfficialPrivateKey` 已填写完整 PEM 内容
- [ ] `AlipayOfficialPublicKey` 已填写正确公钥
- [ ] `AlipayOfficialEnabled` 已开启
- [ ] 已确认后台保存时没有报“参数未配置完整”

### 2.5 微信官方配置

如果你启用了微信官方直连，检查这些：

- [ ] `WeChatPayOfficialAppId` 已填写正确
- [ ] `WeChatPayOfficialAppId` 与当前商户号已绑定
- [ ] `WeChatPayOfficialMchId` 已填写正式商户号
- [ ] `WeChatPayOfficialSerialNo` 已填写商户 API 证书序列号
- [ ] `WeChatPayOfficialPrivateKey` 已填写完整 PEM 内容
- [ ] `WeChatPayOfficialAPIv3Key` 长度正好为 32
- [ ] `WeChatPayOfficialPlatformCert` 已填写平台证书内容
- [ ] `WeChatPayOfficialEnabled` 已开启

### 2.6 人工充值配置

如果你启用了人工充值，检查这些：

- [ ] `ManualTopUpEnabled` 已开启
- [ ] `ManualTopUpAlipayQRCode` 图片 URL 可被公网访问
- [ ] `ManualTopUpWeChatQRCode` 图片 URL 可被公网访问
- [ ] 如果使用固定金额收款码，相关 JSON 已填写且格式正确
- [ ] `ManualTopUpInstructions` 已写明“付款后等待审核”
- [ ] 如只使用人工充值，已清理旧 `PayMethods` 里的 `alipay` / `wxpay`

### 2.7 充值显示配置

- [ ] `Price` 已确认符合当前计价策略
- [ ] `MinTopUp` 已确认不是异常值
- [ ] `AmountOptions` JSON 格式正确
- [ ] `AmountDiscount` JSON 格式正确
- [ ] `TopupGroupRatio` JSON 格式正确
- [ ] 前端钱包页已显示正确的充值档位

### 2.8 前端入口检查

- [ ] 钱包页已显示符合预期的支付按钮
- [ ] 如果走官方直连，官方按钮已出现
- [ ] 如果只走人工充值，不会再出现旧 `submit.php` 入口
- [ ] 如果保留旧 `epay`，按钮名称能让运营看懂哪个是备用通道

### 2.9 小额真实联调

强烈建议至少做 1 元或最小金额真实支付验证。

- [ ] 支付宝官方完成至少 1 笔真实小额支付
- [ ] 微信官方完成至少 1 笔真实小额支付
- [ ] 如保留 `ZPAY`，旧通道也完成至少 1 笔真实小额支付
- [ ] 如启用人工充值，人工审核补单流程也演练过 1 次

### 2.10 到账与状态检查

- [ ] 订单创建后状态初始为 `pending`
- [ ] 支付成功后订单能自动变成成功
- [ ] 用户余额或额度确实增加
- [ ] 订单金额与实际支付金额一致
- [ ] 不存在“用户已付款但系统没到账”的已知问题

### 2.11 日志与排错能力

- [ ] 下单日志可查看
- [ ] 回调日志可查看
- [ ] 异常订单能通过订单号定位
- [ ] 能区分是官方订单、旧 `epay` 订单还是人工充值单

### 2.12 回退方案

- [ ] 如走官方 + `ZPAY` 并行，旧通道仍可立即启用
- [ ] 旧 `PayAddress`、`EpayId`、`EpayKey` 已单独备份
- [ ] 若官方回调异常，有明确的临时回退动作
- [ ] 团队知道回退后该让用户点哪个按钮

## 3. 第二阶段：灰度中检查清单

这一阶段的目标是：

- 小流量真实运行
- 观察成功率和到账率
- 保留快速回退能力

### 3.1 支付成功率

- [ ] 支付宝官方二维码生成成功率稳定
- [ ] 微信官方二维码生成成功率稳定
- [ ] 如保留 `ZPAY`，备用通道仍可用
- [ ] 未出现明显的单渠道大面积失败

### 3.2 到账率

- [ ] 没有连续出现“已支付未到账”投诉
- [ ] 回调到达率稳定
- [ ] 订单状态轮询能正常补偿未及时回调的订单
- [ ] 没有频繁出现 `expired` 但用户声称已支付的异常单

### 3.3 用户体验

- [ ] 用户能分清官方支付和备用支付
- [ ] 如提供人工充值，用户说明文案足够清晰
- [ ] 客服没有大量收到“该点哪个支付方式”的咨询

### 3.4 运营与财务

- [ ] 运营能快速查到订单状态
- [ ] 财务知道当前哪些订单来自官方、哪些来自 `ZPAY`
- [ ] 人工充值补单流程有人负责
- [ ] 灰度期间没有出现明显对账困难

### 3.5 灰度期间不该做的事

- [ ] 没有在第一天灰度时就删除旧 `ZPAY` 配置
- [ ] 没有在尚未稳定前就隐藏所有备用入口
- [ ] 没有在多项配置未验证完时同时大范围开放给全部用户

## 4. 第三阶段：正式切换后检查清单

这一阶段的目标是：

- 主链路稳定
- 旧链路逐步下线
- 后续维护有章可循

### 4.1 正式切换条件

只有满足这些条件，才建议把官方直连作为主链路：

- [ ] 连续多天真实支付成功率稳定
- [ ] 连续多天自动到账稳定
- [ ] 支付宝官方回调稳定
- [ ] 微信官方回调稳定
- [ ] 客服投诉量未明显增加
- [ ] 财务已能顺利对账

### 4.2 清理旧入口前检查

- [ ] 普通充值已不再依赖旧 `epay`
- [ ] 如果你还有订阅支付，已确认订阅是否仍依赖 `epay`
- [ ] 前端不再需要展示旧 `alipay` / `wxpay`
- [ ] 运营和客服已知道入口变更

### 4.3 正式切换动作

- [ ] 把官方支付作为主入口
- [ ] 如不再需要旧 `epay`，从 `PayMethods` 清理旧 `alipay` / `wxpay`
- [ ] 如不再需要 `ZPAY`，最后再考虑清空 `PayAddress`、`EpayId`、`EpayKey`
- [ ] 如果保留人工充值，文案明确说明它只是备用方式

### 4.4 切换后持续维护

- [ ] 定期检查微信平台证书是否需要更新
- [ ] 定期检查支付宝密钥是否仍与应用配置一致
- [ ] 定期检查回调域名和 HTTPS 状态
- [ ] 定期抽查一笔真实支付链路
- [ ] 定期备份关键支付配置

## 5. 最容易遗漏的专项检查

### 5.1 订阅支付

当前项目里，订阅侧仍可能用到旧 `epay` 逻辑。

上线前确认：

- [ ] 已检查 `controller/subscription_payment_epay.go`
- [ ] 已检查 `web/src/components/topup/SubscriptionPlansCard.jsx`
- [ ] 不会因为普通充值切官方，就误伤订阅支付

### 5.2 订单状态轮询

官方支付当前不仅靠回调，还会通过：

- `GET /api/user/topup/status/:tradeNo`

进行状态补偿查询。

所以要确认：

- [ ] 前端二维码弹窗轮询正常
- [ ] 订单状态接口可正常访问
- [ ] 即使回调稍慢，订单最终也能被补偿成功

### 5.3 人工充值兜底

如果你把人工充值作为兜底方案，要确认：

- [ ] 管理员知道如何处理待审核订单
- [ ] 用户知道付款后不会立刻自动到账
- [ ] 有人负责人工审核时效

## 6. 最推荐的上线顺序

如果你还没有自己的上线 SOP，直接用这套：

### 第一天：配置日

- [ ] 完成后台配置填写
- [ ] 完成回调地址检查
- [ ] 不删旧通道

### 第二天：联调日

- [ ] 支付宝官方小额测试
- [ ] 微信官方小额测试
- [ ] 旧 `ZPAY` 小额测试
- [ ] 人工充值演练

### 第三天：灰度日

- [ ] 先让小部分用户使用官方支付
- [ ] 保留旧 `ZPAY` 作为备用
- [ ] 观察到账与投诉

### 第四到第七天：观察期

- [ ] 每天抽查真实订单
- [ ] 每天看回调日志
- [ ] 每天看是否有未到账投诉

### 稳定后：正式切换

- [ ] 逐步隐藏旧入口
- [ ] 最后再清理旧配置

---

## 7. 一句话结论

如果你只记住一条支付上线原则，那就是：

> 先把真实支付、真实回调、真实到账都验证稳定，再去删旧配置和旧入口；不要反过来做。
